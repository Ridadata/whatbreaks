# WB001 — column removed

A column that a model used to produce no longer appears in its output.

## Severity depends on the blast radius

WB001 is not automatically breaking. What matters is whether anything still
depends on the column.

| Situation | Severity |
| --- | --- |
| Something in the change still references it by name | `breaking` |
| Consumers exist but reach it only via `SELECT *` | `possibly_breaking` |
| Consumers existed and the same change updated them | `safe` |
| No consumer, and the whole project was analysed | `safe` |
| No consumer, but coverage was **partial** | `possibly_breaking` |

That last row is the one worth internalising. **Absence of evidence is not
evidence of absence** — if some models could not be read, the consumer may be
among them, and calling it safe would be an overclaim.

## Why `SELECT *` consumers are only *possibly* breaking

`select * from upstream` does not error when a column disappears. It silently
produces a narrower result. That is real breakage, but of a different kind: the
pipeline stays green and the data quietly changes shape. Reporting it as
`breaking` would be wrong; staying silent would be worse.

## Example

```
BREAKING  WB001  column stg_orders.status was removed
          still referenced by: orders; breaks 1 column, 1 model, 1 test
          confidence: likely
```

## Note on confidence

Findings built from SQL that whatbreaks rendered itself are capped at `likely`.
`confirmed` needs dbt-compiled SQL — see [limitations](../limitations.md).

## Prerequisite

A column is only reported removed if the **base** schema resolved exactly. If we
never knew the column was there, its absence is our ignorance, not a finding.
