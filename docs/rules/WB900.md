# WB900 — model could not be analysed

Not a finding about your SQL. A statement about the limits of the analysis.

WB900 fires when a model exists in both commits but could not be compared —
usually because its schema did not resolve exactly on one side, so a
column-level diff would be guesswork.

## Why it is reported at all

Because the alternative is worse. A model quietly dropped from the comparison is
a hole in the answer that looks exactly like "nothing changed here". Naming it
lets a reviewer decide whether to look manually.

This is the same principle as the coverage report: results without their
caveats are a lie by omission.

## Common causes

| Reason | Meaning | Fixable? |
| --- | --- | --- |
| `unparseable_jinja` | a macro we could not resolve offline | often |
| `needs_warehouse` | `run_query` / `adapter.*` — needs a live connection | no |
| `surviving_star` | `SELECT *` over a relation with unknown columns | with `catalog.json` |
| `python_model` | Python model, out of scope | no |
| `sql_parse_error` | sqlglot could not parse it for this dialect | sometimes |

`whatbreaks debug sql --model <name>` shows exactly what was recovered and why
it failed.

## Example

```
    info  WB900  orders could not be compared
          head schema is partial
          confidence: unknown
```
